# Decisions

Each entry: date, decision, why, alternatives considered.

## 2026-09-30: Base image is the unpatched EU disc
- **Decision:** target `Digimon World 2003 (Europe) (En,Fr,De,Es,It)`, single MODE2/2352 track,
  SHA-1 `457cb233349ba841e03b33d8060f8fbcadd45cb3`.
- **Why:** a byte-matching build must target a verifiable, unmodified image. The community
  "dmw2003NTSC" 60fps patch changes only 2 data bytes in the EXE (`0x8005CCAC` video mode
  0=PAL/1=NTSC, `0x8005CCB0` framebuffer offset), so it can be a later build flag.

## 2026-09-30: Project-local toolchain, built from source
- **Decision:** GNU binutils 2.47 (`--target=mipsel-linux-gnu`) and mkpsxiso v2.30 are built into
  `tools/` by `scripts/setup.sh`. Python tools go in `tools/venv` with pins in `tools/requirements.txt`.
- **Why:** no sudo needed, and reproducible on any distro. Fedora/Nobara only packages
  `binutils-mips64-linux-gnu`, which would need wrappers and a system-wide install.
- **Alternatives:** distro packages (sudo), or a Docker image (heavier day-to-day loop).

## 2026-09-30: `asm/` is not tracked
- **Why:** splat regenerates it from the user's disc, and it is derived from copyrighted code.

## 2026-09-30: Symbol and match-status conventions (provisional)
- (Naming superseded by "Naming conventions", 2026-10-01.) splat default names until a symbol is understood. `config/symbol_addrs.txt` is the single source of truth.
- Matching = compiled from C and the whole-EXE build is byte-identical. Non-matching = `INCLUDE_ASM`.
- Progress is computed from the source tree (a script, later), not tracked by hand.

## 2026-09-30: Extract with dumpsxiso `-pt`, no custom extractor
- **Decision:** `scripts/extract.sh` runs `dumpsxiso -pt` (path-table walk) and stores the layout
  XML with relative paths in `extracted/dw2003.xml`. `scripts/rebuild_iso.sh` checks a bit-identical rebuild.
- **Why:** the disc's directory records are obfuscated, so a plain walk finds 3 files. mkpsxiso v2.30's
  `-pt` mode recovers all 2,385, and the rebuild is byte-identical, so no custom extractor is needed
  (the US decomp ships its own `extract_disc.py` for this).

## 2026-09-30: Commit hashes of game files, never the files
- `config/SLES_039.36.sha1` and `config/overlays.sha1` hold the SHA-1s that builds must reproduce.

## 2026-10-01: Independent EU-only project; the US decomp is a reference
- **Decision:** this repo targets **only** SLES-03936 and makes its own tooling and convention choices.
  [juandav/dw3_decomp](https://github.com/juandav/dw3_decomp) (USA, MIT) is a reference: we read its
  findings and may borrow code, but don't depend on it or follow its structure.
- **Why:** the repo stays private until it's far along. Decisions should be ours, on what we consider
  best practice, and the goal is Digimon World 2003, not the US Digimon World 3.
- **Borrowing rule:** anything copied or closely adapted from another project is recorded in
  `docs/THIRD_PARTY.md` (source, commit, license, what was taken) at the time it's borrowed. Then a
  later public release only needs the license notices added, not provenance archaeology.

## 2026-10-01: Toolchain and workflow (approved; details and tradeoffs in `WORKFLOW.md`)
- **Splitting:** splat 0.50 (`splat64==0.50.0`), one YAML per overlay; stage YAMLs generated by script.
- **Compiler:** decompals/old-gcc PSX builds (release 0.17), default `gcc-2.8.1-psx` `-O2`, with
  maspsx for ASPSX emulation. Fully open: no user-supplied SDK needed. To be confirmed for EU by a
  multi-version match experiment (2.7.2 / 2.8.0 / 2.8.1 / 2.91.66 / 2.95.2). Per-file overrides allowed.
- **Tools:** objdiff-cli (+ GUI) for diffs and progress; m2c, maspsx, asm-differ, decomp-permuter as
  pinned git clones installed by `scripts/setup.sh` (no submodules).
- **Build:** `configure.py` generates `build.ninja`. Success = EXE and every overlay match `config/*.sha1`.
- **Psy-Q SDK code:** identified by signatures (psx_psyq_signatures, cross-checked with ghidra_psx_ldr),
  kept as split asm, named, excluded from progress. Not decompiled.
- **Overlays:** separate link unit per overlay at its fixed base, resolving EXE (and parent overlay) symbols;
  overlay symbols get an overlay-name prefix.
- **Dynamic analysis:** PCSX-Redux (Lua, web API, GDB on 3333) is the scriptable oracle; DuckStation for
  accuracy checks. gdb, if needed, is built into `tools/`.
- **MCP:** no emulator MCP for now (scripts instead). Ghidra MCP (pyghidra-mcp) is an optional later trial.
- **Milestones:** M0 = EXE rebuilt from split asm is byte-identical; M1 = `func_800141E4` from C with the EXE still matching.

## 2026-10-01: No Psy-Q SDK and no decomp.me for now; both are fallbacks
- **Decision:** match with the open toolchain only (old-gcc PSX builds + maspsx). We obtain nothing
  proprietary up front.
- **Fallback 1, Psy-Q:** if a function looks unmatchable and we suspect maspsx, get the **matching**
  Psy-Q release (likely 4.3 = GCC 2.8.0/ASPSX 2.77 or 4.4 = GCC 2.8.1/ASPSX 2.79, whichever the compiler
  experiment points to). Copies exist online.
  Run it on Linux via **wibo** (built into `tools/`); wine is the fallback (untested here). Keep it in
  `tools/psyq/` (gitignored), never committed.
- **Fallback 2, decomp.me:** allowed case by case, with the user's approval for each scratch (scratches
  are public). Useful for real Sony compiler presets (Psy-Q 3.3–4.6) and community help. Not a dependency.
- **Why:** most PS1 decomps match with the open toolchain. Both fallbacks cost something (a legally grey
  copy, or making code public), so we only pay it when a real problem needs it.

## 2026-10-01: Worktree support: tools shared from the main checkout
- **Context:** the user works in git worktrees (Orca IDE). A worktree has only tracked files, so the disc
  link, `tools/local.env`, built tools and `extracted/` are missing.
- **Decision:** `scripts/setup.sh` installs tools into the **main checkout's** `tools/` (found via
  `git rev-parse --git-common-dir`) and symlinks every gitignored `tools/` entry into the worktree (`link`
  step, also run automatically at the end). `scripts/worktree_init.sh` = `setup.sh link disc` + `extract.sh`.
  `extracted/`, `build/` and `asm/` stay per-worktree (regenerated, cheap).
- **Why:** builds each tool once (~140 MB, 1+ min), and works wherever the worktree lives.
- **Tradeoff:** tools are shared, so a branch that bumps a pinned version changes it for every worktree.
  Acceptable for a single-user repo; pins are in tracked files, so `setup.sh` on `main` restores them.
- `.gitignore` tool entries have **no trailing slash** (`dir/` patterns don't match symlinks).

## 2026-10-01: Matching-toolchain pins (session 2)
- **Decision:** `scripts/setup.sh` steps `gcc` (old-gcc release 0.17: 2.7.2, 2.8.0, 2.8.1, 2.91.66, 2.95.2,
  SHA-256 per tarball → `tools/gcc/<ver>/`), `objdiff` (objdiff-cli 3.8.2 linux-x86_64, SHA-256 →
  `tools/bin/`) and `ext` (git clones at pinned commits → `tools/ext/`: maspsx `7686f845`, m2c `708d2d2c`,
  asm-differ `0dd09af8`, decomp-permuter `059609d4`, psx_psyq_signatures `e9e46e7e`). Their Python
  dependencies are pinned in `tools/requirements.txt`. `scripts/check_toolchain.sh` is the smoke test.
- **Why:** reproducible and checksum-verified; a commit hash is the checksum for a clone.
- maspsx reads stdin whenever stdin isn't a TTY, so the build always pipes into it. The 2.95.2 `cpp` has no
  `-undef`, so the build uses `-nostdinc` for every version.

## 2026-10-01: Psy-Q 4.7; library names come from our own matcher
- **Decision:** the SDK is **Psy-Q 4.7** (`TOOLCHAIN.md`). `tools/psyq_match.py` generates the library part of
  `config/symbol_addrs.txt` using **4.7's** label names. When several objects match the same bytes, it
  prefers candidates consistent with 4.7, then objects not placed elsewhere, then libraries that are
  certainly linked. Anything still ambiguous stays unnamed, with the candidates as comments. One name per
  address; crt0's internal `stup*` labels are left out.
- **Why:** a wrong name is worse than a default name. The tie-breaks are facts about the link (each object
  is linked once), not guesses. Ghidra's analyzer is a cross-check only, since it takes the first
  candidate when objects tie.
- **Editing:** `symbol_addrs.txt` is hand-maintained from now on. Re-running the matcher prints a fresh
  block to merge by hand; never overwrite the file wholesale.

## 2026-10-01: Milestone 0 build layout
- **splat paths per link unit (target):** `config/<t>.yaml` → `asm/<t>/`, `src/<t>/`, `assets/<t>/`,
  `build/<t>/` (linker script, undefined-symbol files, ELF, map). The EXE is target `main`. Overlays add
  a `Target` in `configure.py` with their own YAML and SHA-1, plus the EXE's symbols as an extra linker
  script.
- **EXE units:** `rodata`, `crt0` (Psy-Q `2MBYTE.OBJ`), `game`, `psyq`, `data`, `bss`, then a `tail`
  segment (`bin`: zero heap area, TIM, padding). Splitting `game` into C-file-sized units comes with the
  decomp work.
- **`.bss` is linked as part of the loaded image** (`ld_bss_is_noload: False`). The EXE header has no bss
  fields and the file holds `.bss` as zeros up to the tail, so this reproduces the file. It also keeps
  splat's ROM position for the tail right without hand-editing the linker script.
- **`subalign: 4`**, with splat's 16-byte section/segment-end alignment turned off. psylink packs objects at
  4 bytes (boundaries at `…E88`, `…F4C`, `…D8C`, `…DCC`, `…CE8`), and GNU as gives each section 16.
- **The payload is `objcopy -O binary` of the ELF.** LMAs are file offsets (header at 0), so the output is
  the whole file, header included.
- **Generated, not tracked:** `asm/`, `build/`, `assets/`, `build.ninja`, `objdiff.json`,
  `include/asm_generated/` (splat's `macro.inc`/`include_asm.h`). `configure.py` re-splits, and
  `build.ninja` regenerates itself when `configure.py`, a YAML or `symbol_addrs.txt` changes.
- **C rule:** `cpp` → `cc1 -O2 -mips1 -mcpu=3000 -G<n>` → `maspsx --aspsx-version=<matching>` → GNU as `-G0`.
  The default is GCC 2.8.1/ASPSX 2.79 and `-G0` (confirmed later the same day, see "Game compiler
  confirmed"), with per-file overrides in `configure.py`. *(Session 5: ASPSX 2.80, no `-fno-builtin`, `-G8`
  for the EXE and `-G0` for overlays; see "Toolchain and -G revised (session 5)".)*
- **Known cosmetic issue:** spimdisasm splits `switch` case blocks that end in `jr ra` off into separate
  `jlabel` "functions" (~150), so as warns about `.end` without `.ent`. When decompiling such a function,
  give the parent a `size:` in `symbol_addrs.txt`.

## 2026-10-01: Milestone 1: C units, compile wrapper, permuter
- **C compile wrapper:** `tools/cc_psx.sh [-V gcc] [-G n] [-MD dep] [-I…] in.c -o out.o` runs cpp → cc1 `-O2` →
  maspsx (the matching ASPSX) → GNU as, and writes one depfile covering headers and `.include`d asm. The ninja
  `cc` rule, `scripts/check_toolchain.sh` and decomp-permuter all use it, so they compile the same way.
- **Units:** a C unit is a `c` subsegment in `config/main.yaml`, named after what the module does
  (`filetable`). Address-named `asm` units (`game_80010F4C`, …) cover the code that isn't split into
  files yet. `make_full_disasm_for_code: True` writes `asm/main/<unit>.s`; assembled into
  `build/expected/main/<unit>.s.o`, that is objdiff's target. The base is the C object.
- Functions kept splat names until the naming convention was decided (see "Naming conventions").
- **decomp-permuter:** `permuter_settings.toml` gives explicit compiler/assembler/objdump commands. (import.py
  can't parse a multi-stage ninja rule, and its defaults are `mips-linux-gnu-*` with `.set gp=64`.) The asm
  prelude is `tools/permuter_prelude.inc`. Work directories (`nonmatchings/`) are gitignored. The
  compiler in `permuter_settings.toml` must match the file's compiler in `configure.py`.
- **Lesson for the compiler-ID experiment:** the permuter made GCC 2.91.66 match `func_800141E4` in under a
  minute, but only with nonsense temporaries. 2.8.1 matches the natural one-line C. So score compilers on
  natural C (m2c output with light cleanup), never on what the permuter can force.

## 2026-10-01: Naming conventions (user decision: option A, snake_case)
- **Modules and files:** short lowercase module names, `src/<target>/<module>.c`, and a header per module,
  created when first needed: `include/<module>.h`. The headers are flat, because module names are unique
  across the whole game. Our own Psy-Q declarations go in `include/psyq/<lib>.h`.
- **Functions and globals:** `<module>_<verb>_<noun>` in snake_case, with the module prefix equal to the file
  name (`filetable_get_lba`, `filetable_lba`). No `g_` or type prefixes; file-local (`static`) symbols follow
  the same rule. Verbs: `get_`/`set_`, `is_`/`has_`/`exists`, `init`, `update`, `draw`, `load`. Words are
  spelled out, except the abbreviations `id`, `lba`, `cd`, `cdloc`, `gpu`, `spu`, `vram`, `tim`, `vab`,
  `mdec`, `pos`, `num`.
- **Types** PascalCase (`typedef struct Foo {…} Foo;`). Fields are snake_case; unknown fields are `unk_<hexoffset>`,
  padding `pad_<hexoffset>`. **Constants** (enum values, `#define`) are UPPER_SNAKE with the module prefix
  (`FILETABLE_COUNT`).
- **Only name what is understood:** otherwise keep splat's `func_…`/`D_…`. An original name found in the
  binary (debug strings, asserts) wins over an invented one. Psy-Q names stay exactly as Sony's. Unnamed
  overlay symbols are `func_<OVERLAY>_<addr>` / `D_<OVERLAY>_<addr>` (session 4: splat's form, see "Overlays link
  against the EXE").
- **Why:** game code is easy to tell apart from the SDK (PascalCase APIs, lowercase libc, `_lowerCamel`
  internals). The prefix is the file name, so it's easy to find in a search. And C has no namespaces, so the
  prefix keeps names unique once the EXE and all overlays are linked into one port binary.
- **Alternative considered:** PascalCase `Module_VerbNoun` (Zelda 64 decomp style), which looks too much like
  the SDK. The US decomp has no game names yet, so there was nothing to stay compatible with.

## 2026-10-01: Game compiler confirmed: GCC 2.8.1 `-O2`, `-G0` by default, `-G8` per file
- *(Superseded in part by "Toolchain and -G revised (session 5)": GCC 2.8.1 stands; ASPSX is 2.80 and the
  EXE's game files are all `-G8`.)*
- **Decision:** the default stays `gcc-2.8.1-psx` + maspsx `--aspsx-version=2.79`, `-O2 -G0`, now confirmed
  rather than provisional. Files that define `$gp` variables (the cluster around `0x8001D3F4`–`0x8001FF9C` and
  `main`'s file) are built with `-G8` through `G_OVERRIDES` in `configure.py`, and define those variables
  themselves (ASPSX only uses `$gp` for symbols defined earlier in the same file).
- **Why:** the compiler-ID experiment (`TOOLCHAIN.md`): 2.8.x matches 68 of 259 functions from unedited m2c
  output, the next best 36, with no function that only another compiler matches. 2.8.0 and 2.8.1 score
  identically, so the choice between them has no effect.
- **Experiment rule:** score compilers on natural C only (m2c drafts with mechanical changes), never on
  permuter output.

## 2026-10-01: Game code file split (session 3, user-approved)
- **Split:** 14 units in `config/main.yaml` (`game_80010F4C`, `game_800120B4`, `cdload`, `filetable`, `game_80014274`,
  `main`, `memcard`, `game_80015590`, `heap`, `pad`, `message`, `gfx`, `sound`, `game_80020B58`), and `.rodata`
  split at the same file boundaries (psylink puts every object's `.rodata`, in link order, before all `.text`).
  `game_<addr>` = a file whose purpose isn't understood yet. Evidence per boundary: `tools/game_xref.py` output
  and the reasoning below. Byte-identical (`scripts/build.sh --check`).
- **Evidence used:**
  - *Rodata alignment:* a jump table sits 8-byte aligned **relative to its object's start**, and objects are packed at
    4 bytes. So a table at ≡4 mod 8 after one at ≡0 means a new object (forces boundaries at rodata `0x84` and `0x160`,
    and one in `0x1A4`–`0x234`).
  - *Section order:* `.data`, `.sdata`, `.sbss`, `.bss` are each in link order, so every file's data comes after the
    previous file's. Each module keeps a table of its own function pointers in its data (`filetable_funcs`,
    `D_80048A78` for memcard, …). The table's position and contents place functions in files.
  - *`$gp`:* ASPSX only uses `$gp` for small variables defined earlier in the same file, so a `$gp` user and its
    variable share a file, and that file is `-G8` (`cdload`, `main`, `gfx` → `G_OVERRIDES`).
  - *Duplicated statics:* `0x80010F4C/0x80010FE0` and `0x800120B4/0x80012148` are byte-identical (a header's static
    fade helpers), each at the top of its file.
  - *No `nop` padding:* game objects aren't padded to 16 bytes (the Psy-Q libraries are), so padding gives no boundaries here.
  - *Cross-check:* the US decomp's file split (juandav/dw3_decomp), mapped by function sizes (330 of 345 match 1:1).
    It agrees with the boundaries at `120B4`, `15590`, `18310`, `19370`, `1D3F4`, `20030`. We differ in two places:
    `0x80014854` is memcard's (first entry of `D_80048A78`; spimdisasm had merged it into `main`), and there is no
    boundary at `0x8001764C` (data `D_8004949C` and table `D_8004B454` span it; `heap` starts at `0x80017B70` instead).
- *Session 4 settled most of these; see "Game code file split: session 4 updates".*
- **Unsure (revisit when decompiling):** whether `game_80014274` is part of `main`'s file; whether `game_80020B58`
  is part of `sound`; whether `cdload` starts at `0x8001345C` (the group `1345C`–`135E8`); the files of
  `18140`–`182C8` (heap/pad), `1932C/1933C` (pad/message), `1D1E4/1D264` (message/gfx); possible sub-files inside `gfx`
  at `1E7E0`/`1ECB0`/`1F738`/`1FD1C` (one `$gp` variable per group).
- **Likely `-G8` too, without `$gp` use:** `memcard` (string `"*"` in `.sdata`) and `message` (2-character SJIS
  strings in `.sdata`). GCC's MIPS port puts any object of size ≤ G in `.sdata`, string literals included. This
  only matters once their data moves to C, so they aren't in `G_OVERRIDES` yet.
- **Not split yet:** `.data`/`.bss` stay one unit each. Note libgte's sine tables (`0x80054888`–`0x80055BEC`) sit
  between two blocks of sound data, which a `.data` split will have to explain.

## 2026-10-01: All game units are C files; rules learned from the first 69 functions (session 3)
- **Every game unit is a `c` segment** (`src/main/<unit>.c`, generated by splat with `INCLUDE_ASM`/`INCLUDE_RODATA`
  for what isn't decompiled). Their `.rodata` subsegments are `.rodata` (the C object's section), as splat's rodata
  migration requires. `crt0` and `psyq` stay `asm`.
- **Data stays in asm; C definitions without an initializer stay COMMON:** `tools/cc_psx.sh` runs maspsx with
  `--use-comm-section`, so a tentative definition such as `Unk8005CD08 *D_8005CD08;` gets no storage in the C object
  and resolves to the asm definition. maspsx still counts it as defined in the file, so `-G8` files reach it through
  `$gp`. That's how gfx's `$gp` functions match.
- **`-G8` files and externs:** in a `-G8` file, cc1 treats every extern of size ≤ 8 as possible small data and emits
  an unsplit `lw/sw sym` macro. That changes instruction scheduling (no `lui` in a delay slot). Where the original
  uses a plain `%hi/%lo` pair, the symbol was not small in the original's view, so declare it with its real larger
  type (`D_80044B38` is a 0x428-byte struct) or an incomplete type (`extern s32 (*D_8004DF98[])(void);`).
  *Open question (settled in session 4: one `-G8` file, no counter-evidence):* `cdload` may not be one `-G8` file (`func_80013780` uses `$gp`; `func_80013C30` reads a small
  extern unsplit).
- **Function-pointer tables are structs:** GCC 2.8 assumes a struct field and a scalar global never alias, so a call
  through a table declared as a scalar can be scheduled across a struct-field store. `D_80055C48` (the sound function
  table) is a struct in `include/sound.h`. (Session 4: the heap table is now the struct `heap_funcs`, see
  "Module state structs".) The scalar `extern`s still used for the heap's table entries
  (`D_8004B5EC` = free, `D_8004B5F4` = alloc, `D_8004B600` = bzero, members of the struct at `D_8004B5DC`) match
  for now but should become one struct.
- **Table entries' types follow the callers:** callers don't mask `filetable_funcs.get_sectors`' result, so it
  returns `s32` (it loads a `u16`).
- **Unknown types are named `Unk<address>`**, after the function that creates them or the variable that holds them
  (`Unk80014504` = the object header that `func_80014504` creates, `Unk80048750` = memcard's state), with fields
  `unk_<offset>`. Rename once understood.

## 2026-10-01: Psy-Q libraries split per library object (session 3)
- **One `asm` unit per library object:** 283 units `psyq/<lib>/<obj>` (lowercase, e.g. `psyq/libcd/s_002` =
  `LIBCD.LIB/S_002.OBJ`), from `tools/psyq_match.py`'s placement plus the 19 settled ambiguous objects. The object
  directory keeps same-named objects apart (`psyq/libcd/sys`, `psyq/libgpu/sys`). Each starts where the previous
  object's 16-byte-padded `.text` ends. `crt0` (2MBYTE.OBJ) keeps its name.
- **`.rodata` per object** (22 objects have some), owned by the object whose code references it, or whose `.data`
  tables point at it: LIBGPU `sys.c`'s `$Id$` string; LIBCD BIOS's command and interrupt name strings, which start at
  `0x80010808`, not where its code's first reference is. Checked: all 42 pointers from `.data` into Psy-Q
  `.rodata` agree, and splat reports no misaligned jump tables.
- **objdiff units are named by path** under `asm/<t>/`/`src/<t>/` (`main/psyq/libcd/sys`). `SDK_UNIT_PREFIXES`
  (`crt0`, `psyq/`) puts them in the `sdk` category. Totals unchanged: SDK 121,496 B / 568 functions in 284 units.
- **Not done:** Psy-Q `.data`/`.bss` stay in the one data unit, like the game's.

## 2026-10-01: Module state structs get a size; callers use their fields (session 4)
- **Pattern:** most game modules keep one struct in `.data`: their state, then their function table, which other
  modules call through. Each such struct gets `size:` in `config/symbol_addrs.txt`, so splat writes `base + offset`
  for every access inside it instead of inventing labels (`D_8004B5EC`), and C uses the struct's fields:
  `heap_funcs` (0x34, `HeapFuncs` in `include/heap.h`), `D_80044B04` (0x34) and `D_80044B38` (0x434, cdload),
  `D_80048D34` (0x275C, gamestate), `D_8004B610` (0x1C0, the object list), `D_8004DE00` (0x10, message),
  `D_8004DE10` (0x190, gfx), `D_80042B1C` (0x8C, `game_800134AC`).
- **Why:** the labels splat made inside these structs were the only difference in 7 otherwise matching functions
  (same instructions, another relocation symbol). Code reaching table entries through the struct's base register
  (`func_8001104C`, `func_800143DC`) shows the original declared them as one object. Scalar externs of table
  entries also break the GCC 2.8 aliasing rule ("All game units are C files").
- **Evidence for each extent:** the table's function pointers in the data asm, and the next variable starting
  exactly where the struct ends. A constant index into an array of records is folded into one address, which is
  why splat labeled `D_80048D34.unk_0760[7].unk_008.unk_3D0` as `D_8004B370`.
- **A struct alone doesn't prove a file boundary:** cdload and gamestate each hold two of them.
- **Shared headers:** types used by more than one file moved to `include/<module>.h` (`cdload`, `gfx`, `heap`,
  `object`, `gamestate`, `game_800134AC`) and our Psy-Q declarations to `include/psyq/lib{cd,gpu,gte,gs,snd}.h`.

## 2026-10-01: Game code file split: session 4 updates (user-approved)
- **New `-G8` unit `game_800134AC`** (`0x800134AC`–`0x80013694`, split off `game_800120B4`): it owns `.sdata`

## 2026-10-02: C patterns learned in session 6 (agents' reports)
- **loop.c hoisting:** an invariant (a global's `%hi`/`%lo` address) is hoisted only when threshold × savings ×
  lifetime ≥ the loop's instruction count (threshold ~29 with calls, −3 per hoisted value). If the original reloads
  an address inside a loop, its loop was bigger or set that register more than once: fix with types (`s16 stat`) or
  by reassigning one pointer, never with `-f` flags. `-dL` shows each decision.
- **Global allocation priority** is `floor_log2(refs) × refs / live length`; `-dl`/`-dg` print it. cse makes the
  longer-lived copy canonical (after `tim = p`, later uses of `p` become `tim`).
- **Operand order:** `x->arr[k]` emits `addu x,k`; `*(x->arr + k)` emits `addu k,x`. Used in
  `gamestate_get_stats` (flagged for review: written only for the operand order).
- A local holding a lui/ori constant stays in one register (cse doesn't rematerialize two-instruction constants).
- A missing argument load can mean the callee takes no arguments: check the overlay definition's prototype
  (`func_8008C000(void)`, called from `gamestate_set_flag`).
- **Small overlays are one file each:** CNTY_SEL, SHOCKTST, SOUNDTST, STAGSLCT have no parity breaks, `.rodata`/`.data`
  referenced in code order and no duplicated helpers (evidence in each config). Their unit is `<target>_<.text vram>`.
- **Strings of `.data` initialisers** are emitted in reverse initialiser order, and GCC shares a function's literal
  with an identical table string; while `.data` is asm, such strings stay `extern` + `INCLUDE_RODATA`. The byte
  before `.text` can be non-zero (a stray byte after the "＞" cursor string in SOUNDTST/STAGSLCT).
- **splat keeps stale `asm/<t>/nonmatchings/*.s`** after a symbol-file change (new `size:`): delete `asm/<t>` or use
  `scripts/build.sh --check`.
- **Shapes:** indexing a table directly (`T[i].a … T[i].b`) loads the base first where a pointer local doesn't; one
  local reused for unrelated jobs shows in the allocation; method calls through the parameter + fields through a cast
  local give two registers.
- **STCRDABM, STFGTREP one file; STDGNAME two** (`0x80082F8C`, `0x80086184`; parity break at jump table
  `0x80082F74`). STFGTREP's candidate break at `0x80085E3C` is contradicted by data order (evidence in configs).
- **Helpers duplicated across overlays** (byte-identical): the `window_anim` pair, fade start/draw/update (also the
  EXE's `func_80011DEC`/`80011E74`/`80011FB8`), the tween pair, the entry point and `update_main` are in nearly every
  tier-1 overlay; `stcrdabm_page_close` also in STCRDSHP/STGMCARD; STDGNAME's `851C4`/`85258`/`83478` in STCRDDEK and
  STPLNMET. Each overlay keeps its own copy (separate link units); a shared overlay header for their types is planned.
- **Don't trust a label-only score:** a unit_diff 99.99% that looked like a jump-table label difference hid a missing
  `default:`; only `scripts/build.sh --check` is proof. Function `.rodata` constants can be `static const` locals.
  `found[count++] = i` and `*p++ = i` differ (loop strength reduction); a variable per switch case stops tail merging.
- **Each tier-1 overlay ends with a "stage module" file** (state, function table, window_anim pair and a value
  start/step pair as the same code each time): STDWTITL `86DF8`, STGMCARD `87C18`, FIELDSTG `91E60`. A small callback
  copied byte-identically into several object groups marks one file per copy (moderate evidence; STDWTITL's 7 files).
- **unit_diff doesn't check function order** within a file; moving a function scores OK but breaks the link. Repeated
  calls/tails in each branch get cross-jumped: write them per branch when the original has them per branch.
- **Object constructors that callers use the result of** return their object (`return obj;` changes no code).
- **Orchestration (session 6):** a usage limit stopped all agents at once; they were resumed from their transcripts
  with uncommitted edits intact. Agent branches are checkpoint-merged (only build-verified commits) so a lost container
  costs only uncommitted work. Shared EXE headers are the merge hot spot: agents should append, not redefine.
- **`D_80042B1C` is three variables** (session 6, integ): state `0x80042B1C` (0x68; `unk_18` = 3 enemies

## 2026-10-04: wip-13 lessons (session 7, permuter-guided pass on CARDGAME/FIELDSTG/EXE)
- **sched1 boost for once-assigned pseudos** (`birthing_insn_p`): an insn setting a live, once-assigned pseudo gets top

## 2026-10-04: Replay runner (layer 2): step scripts, physical buttons, two hashes per checkpoint (session 9, phase 1)
- **Layout:** tests live in `tests/` and `tools/`, never in `src/`, `include/` or `config/`; `scripts/build.sh --check` stays

  and fails on the first failure; a layer whose tool is missing is reported as skipped, and the script fails if nothing ran.
- **Scripts are steps, not raw pad frames.** A script (`tests/replay/scripts/<name>.json`) is a list of `press`,
  `wait_frames`, `wait_stage`, `wait_map`, `wait_mem` and `checkpoint` steps. The waits make the script say *what* it
  waits for (an overlay, a map, a word in RAM) instead of a frame count, so the same script can drive the port, whose CD
  latency differs. The recorded file (`tests/replay/expected/<name>.json`) still has the exact per-frame input trace (as a
  list of changes) and every frame number, so inside one emulator build it is a full determinism check: `--repeat 2`
  must give identical records, and `check` compares everything but the tree commit.
- **Buttons are the physical buttons** (`PCSX.CONSTS.PAD.BUTTON` names). The game rotates the face buttons for every
  language but Japanese (`pad_read_buttons`): physical CROSS is the overlays' "confirm" bit 13 (`PAD_PRESSED(0xD)`),
  TRIANGLE the "cancel" bit 14. Measured in the emulator before being read in the C (a probe pressed every button at
  CNTY_SEL and logged `pad_state.slots[0][0].pressed`).
- **Two hashes per checkpoint:** `gamestate_sha1` over the whole `gamestate_data` (`0x275C` bytes), and
  `gamestate_sha1_stable` with `encounter_timer` (`0x30`) and the playtime fields (`0x48..0x53`) zeroed: those change every
  frame, so the port, which reaches a checkpoint a few frames earlier or later, compares the stable hash first.
  The checkpoint also records the frame, `overlay_module.stage`, `gamestate_data.map` and `pad_random.index` (the RNG
  draw count since boot: the whole random stream is a function of it, DECISIONS "Reference tests").

  per frame. (2) The opening STR movie never finishes: the stream's sectors reach the ring buffer (frame counters grow in

  iteration, so a 2-frame press is one edge in normal screens. (4) Output to a pipe is fully buffered; the runner sets

- **Memory cards:** the driver gives every run fresh cards in its output directory (`-memcard1/-memcard2`); the user's

## 2026-10-05: Layer-1 oracle: Lua-driven calls on the real game, not a PS1 test EXE (session 9, phase 2)
- **Decision:** goldens are produced by calling the game's own functions **inside the running game** from Lua
  (`tests/golden/oracle.lua` under PCSX-Redux), option (a) of STATUS "Next" 0, not by a separate PS1 test EXE linking the
  matching objects (option (b)). (b) was costed: compiling `pad.c`, `memcard.c`, `gamestate.c` and
  `fightstg_8008D3B4.c` standalone with `tools/cc_psx.sh -V 2.8.1` leaves 14, 15, 14 and 41 undefined symbols each, so
  every family needs stubs plus a link script, a loader and a result channel, and the stubs are exactly where a test EXE
  can diverge from the game. (a) needs none of that: the real callers' data (tables, globals, overlays) are all in place,
  and an overlay family only needs the overlay file copied into its slot.
- **Mechanism:** boot the disc with `-debugger -interpreter` (breakpoints never fire under the dynarec, even with
  `-debugger`), wait for CNTY_SEL (stage 22, first word of the slot `0x80083DC0`: the EXE is resident and idle), then an exec
  breakpoint on `pad_update` takes over the main loop. Per job: save the regions the job may write, apply the fixture and
  the scratch buffers (`0x80180000`, free heap above the overlay slot), set `a0..a3`, `ra = 0x80010000` (the EXE's
  `.rodata` start: never executed, so an exec breakpoint there is the return sentinel) and `pc = function`; at the sentinel
  record `v0`/`v1`, read back memory, restore. `PCSX.addBreakpoint`/`PCSX.getRegisters()` (`src/core/pcsxffi.lua` at
  `bf4c9ceb`) give exactly this; registers are writable cdata. All families run in one boot (718 jobs, ~20 s wall).
- **Independence of cases:** every case is one job with its own fixture and save/restore, so a function with side effects
  (`gamestate_check_condition` type `0x13` marks a Digimon joined) cannot leak into the next case; the write is still
  recorded as `gamestate_data`'s SHA-1 after the call. Conditions that change money (type `0x20`) or need a live object
  (`0x50`) are excluded from the family rather than run with a partial fixture.
- **Golden format:** JSON per family, `tests/golden/<family>.json`, tagged with the method, the emulator build, the BIOS
  and the matching tree's commit (`git log -1 -- src include config`); fixtures deduplicated into a family-level table.
  `check` ignores the tree commit and the BIOS: a doc-only commit changes nothing, and the retail BIOS must reproduce the
  OpenBIOS goldens (it does, for all 1,106 calls). `gen` refuses any BIOS but OpenBIOS. The first three families
  (`pad_random`, `memcard_checksum`, `gamestate_flags`) were generated twice and reproduce exactly.
- **What this does not prove:** a golden records what the original does for a fixture; it says nothing about which of
  the game's own inputs reach that fixture in play. The replay layer covers that end.

## 2026-10-05: Overlay goldens by kept setup jobs; the host-side replay (session 9, phase 3)
- **Overlay families load the overlay themselves.** A golden case can be *kept*: its writes are not restored, and a write
  can be a file's bytes. The battle family's first case copies `FIGHTSTG.PRO` into the overlay slot (`0x80082CB0`; its
  `.data` and zero variables are inside the file, nothing to clear) over the CNTY_SEL overlay the game was running, and
  puts `SDIGIEDT.PRO` (the enemy records, file `0x1CF`) at `0x80190000` with a `cdload_module.entries[]` record marked
  loaded, so `cdload_module.files.get_file(0x1CF)` returns it without a CD read. The card family does the same with
  `CARDGAME.PRO` and the card files `0x7F6`/`0x7F7`. Safe because the hijacked main loop never returns to the slot's code
  (every call chains from the sentinel and the run ends with `PCSX.quit`); verified by a smoke call in each setup case
  and by hand-computed results (`fightstg_rules_get_damage` basic attack 114, card scores 30/36/88). Families keep their
  jobs contiguous, so a family's setup precedes its cases whatever else runs in the boot.
- **Per-call writes.** A call carries its own writes, applied just before it and restored with the case, so one shared
  fixture (deduplicated into the family's `fixtures` table) serves a grid of variations without a fixture per case.
- **The oracle's symbol table** covers `config/symbol_addrs.txt` and every `config/<overlay>.symbols.txt`; a name two
  overlays define at different addresses is refused rather than guessed.
- **Host-side replay (B5), `tests/host/`:** the same C compiled with gcc for this machine, with `-m64` (no 32-bit libc
  here; `gcc-multilib` would need a system install), driven over stdin by `replay.py` through the golden cases, every
  result compared. Design points: the symbol table is generated from the goldens' names (`extern char name[]`, the
  linker's view, no headers); undefined externals of the big units resolve to 0 at link time instead of a stub each
  (`--unresolved-symbols=ignore-all`: a reached one crashes loudly); the shims supply the heap (libc), the file loader
  (files registered from the goldens' cdload entry writes), time, and a few stubs; fixture writes to raw addresses are
  skipped; the goldens' own `saves` restore the host's state between cases. LP64 makes pointer-bearing structs wider:
  fixtures stay in pointer-free prefixes (hence `gamestate_data` reads stop at `.funcs`), and the one buffer of such a
  struct (`CardgameGame`) is remapped with offsets a compiled `layout.c` reports and cross-checks.
- **Fixtures must be complete.** The first host run differed on every gamestate case because the fixture wrote only the
  fields it cared about and the rest was the game's state at CNTY_SEL versus the host's initializer. The fixture now
  zeroes the whole pointer-free `gamestate_data` first. Rule for new families: write everything the function may read.
- **Findings policy:** a mismatch is recorded in `tests/host/FINDINGS.md` with its cause, and its cases go in
  `tests/host/known_mismatches.json`, so `scripts/test.sh` fails only on a *new* mismatch. `src/` is never changed for
  it (CLAUDE.md: the matching build is the reference); the port decides. First finding: `gamestate_check_party_stat`
  reads past its 15-entry table for flag indexes >= 15, into `gamestate_data` on the original.

## 2026-10-05: Session 10 oracle lessons: buffer reads, kept cases, the vsync timer, tables at a file's end
- **Output buffers are read back.** A `Read` may name a scratch buffer (`buf:<name>`) instead of a symbol; the oracle
  resolves it to the buffer's address and the host harness's `D` command accepts the same name. Functions that fill a
  caller's struct (`gamestate_get_stats`, `gamestate_list_forms`, `records_list_items`, `gamestate_add_stat_bonus`) are
  tested on what they wrote, not only on their return value.
- **A kept setup case writes only the overlay.** A kept job restores nothing, not even its `saves`, so a fixture written
  by it would leak into whatever runs next. The family's fixture goes on every ordinary case instead (deduplicated into the
  golden's `fixtures` table), and the setup's smoke call is `void` with no reads: its result depends on the resident state
  and is not compared on the host.
- **The game keeps running under a long call.** The oracle stops the main loop, not the interrupts: gfx's vsync handler
  adds `0x133` to `gamestate_data.playtime_frames` every vblank, so a call long enough to span one (a level-up from 1 to
  99 rolls 98 x 15 draws) returns with that word changed. The whole-struct hash is taken in two reads around offset
  `0x48` in the families that have long calls (`gamestate_records`, `stfgtrep_exp`). The emulator is deterministic, so the
  golden itself was stable; only the host (no timer) showed it. `gamestate_tick_playtime`'s own cases read the word on
  purpose; their calls are a few dozen instructions, so a vblank inside one is unlikely and would show as a stable golden
  the host disagrees with (the fix would be to move the field out of the fixture's reads).
- **Reads past a table are findings, not bugs to fix.** `stfgtrep_resist_gains` ends the overlay file, so the original
  reads 0 past it (`.bss`) and the host reads garbage (`tests/host/FINDINGS.md` 2). The golden records the original; the
  mismatching cases are listed by exact name in `known_mismatches.json` (a `where` ending in `:` matches one case), so a
  prefix never hides a new mismatch in a neighbouring case.

## 2026-10-05: M0 facts and the M1 skeleton's design (session 15, agents T0-T9)
- **Hook macros live in `include/port.h`, included from `common.h`;** each is the exact PS1 code without `PC_PORT`. A
  function in an overlay slot is a *tag* on the host (the PS1 address in the function pointer, a constant expression for
  the static tables) and is only ever called through `OVERLAY_FN`/`LATE_CALL`, which resolve it in the current overlay.
  `SLOT_PTR`/`HEAP_*` are constant expressions on both sides because the arena's buffers are link-time symbols.
- **GCC 2.8.1 facts found while moving data to C** (all byte-identical in the end): a 4-byte `const` goes to `.sdata` at
  `-G8` unless the section is named (`main.c`'s `MAIN_RODATA`); a `const` word must be defined after the functions whose
  jump tables precede it in `.rodata` (source order); a C `.rodata` definition placed right before an `INCLUDE_ASM` whose
  asm carries `.rodata` makes GCC omit the next `.rdata` directive, so the following functions' literals land in `.text`
  (SHOCKTST: the word is typed `asciz` in the symbol file so splat migrates it into the holdout's asm instead); strings
  followed by psylink's non-zero fill become `const u8[N]` arrays with the fill spelled out (the "stays INCLUDE_RODATA"
  rule for the two cursor strings is superseded). The EXE matrix block `0x8004DC10` is C at the start of `message.c`'s
  `.data` (owner still a guess). FIELDSTG's zero block stays asm: psylink's "IN" fill sits inside one `.bss` run, which GNU
  ld cannot reproduce without a FILL facility in `configure.py`.
- **Method slots keep word-sized parameters** (`cardgame_board_open_dialog`, `set_dialog_answer`, `stdwtitl_menu_get_result`,
  `gfx_set_clip_*`): narrowing a slot's parameter types changes the callers' bytes, so the assignments carry explicit
  casts; the host calls an `s16`-parameter function through an `s32` pointer (UB that GCC's callee re-extension tolerates).
  `CardgameGame.opponents` is a pointer field (byte-identical retype). `object_create`'s `child_count` is `data_size / 4`
  on the PS1 and `data_size / sizeof(void *)` on the host; a data block mixing `s32` and pointers is still a port hazard
  (FINDINGS 9c).
- **The probe is a gate:** `tools/port_inventory.py probe` (`-m64`, `-Werror` on pointer/int casts, implicit declarations,
  incompatible pointer types; `-fpermissive` only on GCC 14+ so the gate is the same on CI's GCC 13) and `link` run first
  in `scripts/test.sh` and as a disc-free CI step. They need no `include/asm_generated/`.
- **The port runtime (`port/`):** the arena mirrors the PS1 layout from `0x80082CB0` (slots at the PS1 distances, a 4 MB
  heap) in one 16 MB-aligned non-PIE `.bss` block; PS1-style addresses are base + offset. Overlay data isolation is a
  generated GNU ld script (`.dw3.data/.bss.<ovl>` inserted before `.data`/`.bss`); the snapshot is taken before
  `game_main`. The address tables are generated at build time from the symbol files filtered by `nm` of the objects, and
  the build fails if a tag site in the C does not resolve. `src/main/main.c` is compiled with `-Dmain=game_main`.
  Loops the game ends only by a CD interrupt carry `PLATFORM_WAIT()`; the runtime's watchdog (exit 4) catches the ones
  that do not. LIBC2/LIBAPI are the host libc (a definition in the executable would interpose on every shared library).
- **Agents on this machine:** 32 cores and 125 GB allow 5 worktree agents at once with `DW3_JOBS=6`
  (`scripts/build.sh --check` takes 22 s on ~12 cores, 110 MB peak per process); `docs/AGENT_BRIEF.md`'s `DW3_JOBS=1` is
  the shared-4-core default, overridden per brief.


## 2026-10-06: M1: the headless port replays new_game (session 16, agents T1-T5)
- **What the port test compares** (`tests/port/run.py`, the `port` layer of `scripts/test.sh`, a CI step): the port
  replays `tests/replay/scripts/new_game.json` from `--disc` twice; the two logs and records must be byte-identical, and
  the record's **cross-core view** (`replay.py`'s own `cross_core_view`/`compare`: each checkpoint's name, stage, map and
  stable `gamestate_data` hash; the overlay and map sequences without frames) must equal `tests/replay/expected/new_game.json`.
  Frames, `random_index`, the full hash and the inputs are not compared, as between the emulator's two cores (the port's
  CD timing differs again: 1,831 frames against 2,462). `--m32` also requires the 32-bit build's log and record to equal
  the 64-bit build's; `--sanitize` requires no ASan/UBSan report. Movies are streamed but not decoded; the script skips
  the opening movie with START as in the emulator.
- **The checkpoint hash is of `gamestate_data`'s PS1 image:** its first 0x26FC bytes (no pointer before `funcs`, which
  sits at 0x2700 at `-m64`), then the 24 `funcs` entries as the PS1 addresses of the host functions (a table generated
  from `config/symbol_addrs.txt`, filtered by `nm`). Checked on all five of the emulator's dumps (T2).
- **A frame is a vsync tick** wherever it comes from (`VSync()`, `PLATFORM_WAIT()`, LIBCD's `StGetNext` every 5000 empty
  polls); `port_frame` (`port/src/pump.c`) runs the CD tick, the log and the script on each, as run.lua's vsync listener.
- **CD latency is simulated in vsync ticks, deterministically** (`--cd-speed`, `port/psyq/libcd.c`): `realistic` (the
  default) delivers the Setmode speed (bit 0x80: 3 sectors a tick, else 1.5) after a seek of 3 + distance / 8192 ticks,
  at most 40, following a Setloc (a stand-in: psx-spx gives no formula); `instant` has no seek and up to 75 sectors a
  tick. Each sector calls the ready handler once; a command from a handler stops the delivery. Movies stream from the BIN
  at the drive's rate into the game's own `StSetRing` buffer (StHEADER + data per frame, XA sectors skipped): the opening
  movie plays its 1,776 frames at exactly 15 fps. The disc's SHA-1 (`457cb233...`, as `setup.sh`) is checked at every
  start, with a stamp cache in `$XDG_CACHE_HOME/dw2003-port/` keyed by path, size, mtime, inode and device.
- **Pinned quirks the port reproduces** (each under `PC_PORT`, byte-identical on the PS1, or in `port/`):
  - the R3000A's division by zero (`x % 0 == x`, FINDINGS 7): the first battle's end takes its draw and gives no item;
  - `void` object creators whose callers use `v0` return the object on the host (`OBJECT_V0`, 36 + 5 overlay entries,
    FINDINGS 8);
  - `object_destroy` stops exactly the live objects the PS1's 4-byte word scan stops (FINDINGS 9c: a byte scan of the
    block checked against the heap's live objects), and objects created with size 0 get their real size (9a, 9b);
  - FIELDSTG reads a NULL map-event list as empty (the PS1 reads low RAM, 0 there in the emulator);
  - the overlay copy's CPU time: LIBC2's byte-loop `memcpy` (~12 cycles a byte) keeps the emulator one or two frames in
    the state between the copy and the overlay's start-up, and a checkpoint (`new_game_field`) sees that state, so the
    overlay manager runs `size * 12 / 677376` vsync ticks after a copy;
  - STPLNMET's trim from `name[19]` of a `u16[12]` reads the same half-word on the host (FINDINGS 10: nothing to do).
- **Data sizes are host sizes** (FINDINGS 9d): every `object_new`/`object_create` size is in `sizeof` units that equal the
  PS1 value (122 sites), and `tools/port_inventory.py object-sizes` fails on a bare literal; the host heap is 8-aligned
  (`HEAP_ALIGN`); overlay entries return `Object *`; `OFFSETOF` (`common.h`) for a partial clear whose prefix holds
  pointers (`fieldstg_find_stage`).
- **The primitive-stream hash ignores bits the GPU ignores** (the padding halves of textured polygons' texture words),
  or heap leftovers make `-m32` and `-m64` differ.
- **The pad is a frame late, as in the emulator:** LIBPAD reads the controllers in the vsync interrupt, before the
  replay runner's vsync listener sets its override, so the game sees the buttons one frame after the runner chose them.
  `psyq_pad_set` therefore latches, and the buffers are filled at the next vsync. Without it every `walk` ended a few
  pixels off (the emulator's trajectory, frame by frame, showed the extra frame) and `first_battle_save` missed the
  Tamer Service counter; with it the port matches that script's first six checkpoints, the scripted battle included.
- **The script engine** (`port/src/script.c`) is run.lua's in C: every step but `reset` (exit 6; it would need the whole
  runtime restarted). `walk` reads FIELDSTG's player actor from `heap_objects`. `wait_mem` reads only layout-identical
  ranges (`port_state_read`); `memcard_state` and overlay data are not mapped yet.
- **This machine (cloud, session 16):** 4 cores, 15 GB: 3 worktree agents at once with `DW3_JOBS=1`, `-j2` for the port.
  `gcc-multilib` installed by the user's approval (apt, root); ASan/UBSan were already present. The `Agent` tool's

## 2026-10-06: first_battle_save in the port: memory cards, the reset, the file cache (session 16, agents T6-T8)
- **The port replays both layer-2 scripts.** `first_battle_save` (the first battle, a save, a reset, the reload, the
  shop, the lab, the card album and deck editor, the card shop, training) matches all 20 checkpoints and both sequences
  of `tests/replay/expected/first_battle_save.json`; `tests/port/run.py` runs every script with an expected file.
- **Memory cards are raw 128 KB `.mcd` images** (`port/src/memcard.c`, `port/psyq/libmcrd.c`; `--memcard1|2 PATH|none`,
  default a fresh card in memory as the replay runner gives PCSX-Redux). A fresh port card is byte-identical to
  PCSX-Redux's; saves move both ways (the emulator loads the port's save and vice versa, the `loaded` checkpoint equal).
  LIBMCRD's commands complete after a fixed number of `MemCardSync` polls (the game spins on them); the first access
  after insertion or reset answers McErrNewCard (3), as the emulator's run shows.
- **The reset** (`port/src/reset.c`): every game section (`.data`/`.bss` of the EXE units and the overlays, in output
  sections of their own) restored from the startup snapshot, the arena cleared, every Psy-Q library back to power-on,
  the cards and the disc kept, then `game_main` again (a longjmp from the vsync tick). `tools/port_gen.py sections`
  checks the link map at every build: no game data outside the restored sections. A run after a reset is byte-identical
  to a fresh one; the BIOS boot time is not modelled (frames are not compared).
- **The file cache frees its oldest file when its 64 entries are full on the host** (`cdload_queue_file`, `PC_PORT`):
  the PS1 frees cached files only when the heap runs out, which its 1.3 MB does before 64 files; the port's 4 MB heap
  never does. Only which files stay cached changes, so only the CD timing.
- **Views of two objects as one cannot work on the host:** STGMCARD declared `memcard_state` as a struct holding
  `memcard_state` and `memcard_funcs` (adjacent on the PS1); under `PC_PORT` it uses the two objects' own types.
- **The `-m32` build found a 64-bit assumption in the port's own code** (`object_destroy`'s scan skipped the word after
  a live object, as if every pointer were 8 bytes): the 32-bit build never ended a FIELDSTG event. Comparing the two
  builds' logs is the cheapest layout check there is; it runs in CI.
- **UBSan's reports of the game's own in-struct overruns are suppressed by name** (`tests/port/ubsan.supp`: FINDINGS 5
  and 10 only); any other report fails the port test.
- **The GTE is needed for game logic, not only drawing** (FIGHTSTG's fade interpolates with `gte_gpf12`): with the no-op
  macros the result was stack garbage that differed between builds. `port/psyq/gte.c` (T8) is a software GTE written
  from psx-spx (every command, FLAG, saturations, the UNR division): the `gtemac.h` macros reach it by mechanical
  translation of their MIPS (`tools/port_gen.py overrides`), and the layer-1 family `gte` (865 cases: MIPS routines in
  scratch RAM run on the PS1) pins it; the host replay checks it at -m64, -m32 and under the sanitizers. What the
  goldens corrected: the MAC accumulator wraps at 44 bits, LIBGTE's `RotMatrix*_gte` floors each product, `ScaleMatrix`
  writes `MATRIX`'s pad halfword. A model's first animation step blends with parts nothing wrote (the PS1's heap
  leftovers): the host zeroes them (`fightstg_model_new`, `PC_PORT`; drawing only). LIBGS's GTE set-up
  (`GsSetProjection`'s H, `GsSetFlatLight`'s colour matrix) is left for M2, checked the same way.
- **The file cache depends on heap addresses** (FIELDSTG's `cdload free_above(0x8015C674)` frees the cached files placed
  above that address): the host's layout differs from the PS1's at either pointer width and between the two, so which
  files stay cached, hence the CD timing and the frames, can differ by build. The game state does not: `-m32` and
  `-m64` reach the same 20 checkpoints. `tests/port/run.py --m32` therefore requires the same cross-core view for every
  script and byte-identical logs for `new_game` (the M1 criterion); the sanitizer build (the `-m64` layout) stays
  byte-identical everywhere.

## 2026-10-06: M2: the software GPU and the SDL3 window (session 16, agents T9-T10)
- **The GPU's oracle is the emulator's software GPU** (`port/psyq/gpu.c`; layer-1 family `gpu`: 715 cases run through the
  game's own LIBGPU in PCSX-Redux, VRAM read back with `StoreImage`, replayed on the host by `tests/host/gpu_replay.py`).
  Where psx-spx is silent or disagrees, the emulator's measured rules are taken (exact ceil coverage with the top-left
  rule, a quad as triangles (1,2,3) then (0,1,2), vertex + offset wrapping at 11 bits, dithering only for Gouraud
  primitives through an 8-bit pipeline, unclamped modulation before the blend, Gouraud-textured spans coloured per pixel
  pair, the lines' own stepping), except three hardware rules kept (the fill's x rounded down to 16 and wrapping, copies
  obeying the mask bits and wrapping, a 1x1 draw area drawing its pixel). 133 cases stay known mismatches, each with its
  reason (`tests/host/known_mismatches.json`: interpolation at .5, the emulator's paired-pixel blend carries in modes 2/3
  on modulated textures, the three kept rules). The whole VRAM equals the emulator's at seven points of `new_game`.
- **Execution adds to recording:** `DrawOTag` hashes the primitive stream exactly as in M1, then executes it. The PS1
  library's own packets are reproduced (`SetDrawEnv`: E3, E4, E5, E1, E2, E6 and a TILE when `isbg`, so every frame's
  primitive hash changed once; `SetDefDrawEnv`'s `dfe = h < 289`; `ClearImage` as TILE or fill by alignment);
  `BreakDraw` returns 0 (the GPU is idle), so FIGHTSTG's cursor copies are drawn. A headless run costs ~0.5 ms a frame
  more (`first_battle_save`: 2 s -> 22 s); `gpu.c` builds at `-O2` inside the `-O0` port.
- **SDL3 3.4.18, static, in `tools/sdl3`** (`scripts/setup.sh sdl3`: the signed release tarball, its SHA-256 pinned; the
  backends load at run time; missing optional backends are turned off at configure time). `-DDW3_PORT_SDL=ON` is opt-in:
  the headless build and every test stay SDL-free; CI builds the SDL variant and runs its `--input-test`.
- **The window** (`port/src/video.c`, `input.c`): the display area of the VRAM (15- and 24-bit; `DISPENV.disp.w` counts
  screen pixels, a 24-bit area spans `w * 3 / 2` VRAM pixels), 4:3, integer-scaled by lines (default 2), real-time pacing
  at 50 Hz only with a window (a window run's log is byte-identical to a headless one's), keyboard and gamepads merged
  into pad 0 (logged like a script's inputs; a script owns the pad when given). `--screenshot FRAME:PATH` works headless.
